# ADR-0002: Кэширование ответов checko (PSR-16, Valkey, TTL 1 час)

- **Статус:** Принят
- **Дата:** 2025-11-25
- **Связанные документы:** [ADR-0001](0001-wrap-checko-api.md), [GLOSSARY](../GLOSSARY.md)

## Контекст

- Каждый успешный запрос к checko (`HTTP 200`) **платный**; бесплатно — 100 запросов в сутки.
- Технический лимит — 32 запроса в секунду с одного IP, сверх — `429`.
- Данные checko (ЕГРЮЛ/ЕГРИП, финансы, суды) меняются нечасто: актуальности «в реальном
  времени» для обёртки не требуется.
- Повторные одинаковые запросы (демо-страница, ручные проверки, ретраи клиентов) — типичный
  сценарий, и они не должны стоить денег.

## Решение

Кэшировать успешные ответы checko в Valkey через **PSR-16** (простейший интерфейс, без
привязки домена к Valkey).

- **TTL:** 1 час (3600 секунд) для всех ресурсов. Единое значение — константа в конфиге,
  не размазано по классам.
- **Ключ кэша:** `checko:v2:<resource>:<sha256(normalized_params)>`, где:
  - `resource` — путь checko (`company`, `contracts`, ...);
  - `normalized_params` — параметры после `buildParams()`, отсортированные по ключу
    (детерминированный порядок);
  - **ключ checko (`key`) в ключ кэша не попадает** — иначе секрет утекает в хранилище, а
    смена ключа сбрасывала бы весь кэш.
- **Что кэшируем:** только ответы с `HTTP 200` и `meta.status = "ok"`, **после** успешного
  маппинга в DTO. В кэш кладётся сырой блок `data` из checko: маппинг уже подтвердил его
  корректность, а для чтения из кэша не нужен второй гидратор вложенных value-объектов.
  Ошибки, 404 и частичные ответы не кэшируются — «не найдено» может стать «найдено» через
  минуту.
- **Где кэш в конвейере:** Facade: `validate → buildParams → cache.get → (miss) Transport →
  map → cache.set → return`.
- **Fail-open:** если Valkey недоступен или отдал ошибку, логируем и идём в checko без кэша.
  Доступность API важнее экономии; падение кэша не должно ронять сервис.
- **Инвалидация:** только по TTL. Ручной сброс не нужен: данные не меняются в пределах
  часа, а административная ручка «purge» не оправдана для тестового задания.
- **Версионирование:** префикс `v2` в ключе — при смене формата DTO/маппинга ключ меняется,
  старые записи умирают по TTL сами.
- **Наблюдаемость:** в лог — только `cache hit/miss` (без тела ответа и без ключа checko).

## Почему так

- 1 час — компромисс: заметно снижает расход платных запросов и риск `429`, но данные
  остаются достаточно свежими для юридических реестров.
- PSR-16 позволяет заменить Valkey без правки домена (см. ADR-0001).
- Кэширование после маппинга гарантирует, что в кэш не попадут данные, которые DTO отверг.

## Последствия

- Минус: данные могут отставать до 1 часа — для юридических данных приемлемо, и это
  осознанно зафиксировано здесь.
- Плюс: повторные запросы не тарифицируются и не упираются в лимит 32 rps.
- Плюс: `meta.balance` / `meta.today_request_count` из ответа можно логировать для контроля
  расходов (не кэшировать — это метрики, а не данные).
